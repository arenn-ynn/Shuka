SHUKA MARKETPLACE — COMPLETE LOCAL & RENDER DEPLOYMENT GUIDE
==========================================================

IMPORTANT: Read all of Parts A–D before deploying. The Render service MUST be
paid and MUST have a persistent disk. A free Render service loses uploaded
images and SQLite data. Never publish your .env file or demo passwords.

PART A — UNDERSTANDING THE PROJECT
-----------------------------------
Shuka-Marketplace/
  frontend/src/main.jsx     React storefront and seller dashboard; real API calls
  frontend/src/style.css    Responsive styling for desktop, tablet, phone
  frontend/vite.config.js   Vite build and local development proxy
  frontend/dist/           Generated by npm run build (not committed)
  backend/server.js        One Express server: authentication, API, photos, UI
  backend/db.js            SQLite connection, WAL, busy timeout, migrations
  migrations/001_schema.sql Ten mandatory SQLite STRICT tables
  migrations/002_sessions.sql Hashed, revocable login sessions
  scripts/migrate.js       Apply SQL migrations (safe to repeat)
  scripts/seed.js          Demo sellers, buyers, categories, 54 product entries
  scripts/backup.js        Consistent point-in-time SQLite backup
  tests/acceptance.test.js Real HTTP and database acceptance tests
  render.yaml              Render Web Service with paid persistent disk
  .env.example             Configuration example, never actual secrets
  .gitignore               Excludes secrets, SQLite, images, node_modules
  package.json             npm scripts and dependency versions
  package-lock.json        Lockfile metadata (see install note in Part B)
  README.md                Project summary and API notes

The app uses only ONE long-running Node process in production, on port 3000
locally. /api/* are JSON endpoints; /uploads/* serves local images. The built
React site is served by the SAME Express process. Database and photos are files
on disk, not third-party APIs. Prices use whole AMD integers.

PART B — RUN LOCALLY ON YOUR MAC
--------------------------------
1. Download Shuka-Marketplace-Complete.zip. Open Terminal. If it is in Downloads:

   cd ~/Downloads
   unzip Shuka-Marketplace-Complete.zip
   cd Shuka-Marketplace

2. Confirm Node >= 20, then install dependencies:

   node --version
   npm --version
   npm install

   npm install creates/updates package-lock.json. This ZIP's initial lock
   metadata may be regenerated by npm install because registry access was
   not available in the creation environment. Commit that updated lockfile.

3. Make your own local environment file:

   cp .env.example .env

   If you want to set a secure secret for local use:

   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

   Copy the printed string. Open .env with `nano .env`, replace the example
   COOKIE_SECRET value with the string; save with Ctrl+O, Enter, Ctrl+X.
   NOTE: Node does not load .env automatically in this project. For local
   use the default development settings work without environment variables.
   To load your .env into the current shell before running commands:

   set -a; source .env; set +a

4. Initialize the database and create realistic demo data:

   npm run db:migrate
   npm run db:seed

   Expected data path: ./data/shuka.sqlite; photos: ./data/uploads/.
   The seed creates 3 sellers, 2 buyers and at least 40 product entries.
   Demo password (LOCAL DEVELOPMENT ONLY): ShukaDemo2026!
   Demo emails:
     seller1@shuka.demo
     seller2@shuka.demo
     seller3@shuka.demo
     buyer1@shuka.demo
     buyer2@shuka.demo
   Change the seed password *before the first seed* by setting SEED_PASSWORD
   in your shell. Existing demo passwords do not change on reseeding.

5. Build and run the production-style app locally:

   npm run build
   npm start

6. Open http://localhost:3000 (exact URL). Local dev alternative:

   npm run dev

   For npm run dev, the frontend is http://localhost:5173; API on port 3000.

7. Stop with Ctrl+C in Terminal. Restart by returning to the directory and:

   set -a; source .env; set +a
   npm start

8. Test the actual HTTP service and SQLite behavior:

   npm test

   Tests create their own temporary database; they do NOT erase your local
   demo data. They also exercise concurrent checkouts and image rejection.

PART C — CREATE AND PUSH YOUR GITHUB REPOSITORY
------------------------------------------------
1. In a browser, open https://github.com and sign in (or create an account).
2. Click + > New repository. Name: shuka-marketplace.
   Choose Private or Public. Do NOT add README, .gitignore or license online;
   these are already in the project. Click Create repository.
3. In Terminal, in the extracted Shuka-Marketplace folder, run:

   git init
   git branch -M main
   git add .
   git status

   Make sure .env, data/, uploads/, backups/ and node_modules/ are NOT listed.
   Then:

   git commit -m "Build Shuka marketplace"
   git remote add origin https://github.com/YOUR_USERNAME/shuka-marketplace.git
   git push -u origin main

   Replace YOUR_USERNAME with your real GitHub username. If you are asked to
   authenticate, follow GitHub's browser login flow. Never paste a password
   or token into your source files.

4. DO NOT COMMIT: .env, real session tokens, real passwords, SQLite database,
   WAL files, uploaded images, backups or node_modules. Commit migrations,
   source files, package-lock.json and render.yaml.

PART D — DEPLOY THE WEB SERVICE ON RENDER.COM
---------------------------------------------
Recommended: one PAID Render Web Service (Starter or another paid plan) with
1 GB or more persistent disk. This is NOT compatible with Render Free.
Check current pricing at https://render.com/pricing before subscribing.

First deployment (Render WEBSITE, unless indicated):

1. Create/sign into an account at https://dashboard.render.com.
2. Click New > Web Service and connect your GitHub account. Authorize access
   to your shuka-marketplace repository and select that repository.
3. Choose a clear name, e.g. shuka-marketplace, branch main.
4. Runtime: Node. Root directory: repository root (leave blank).
5. Compute: paid Starter tier or higher. Do NOT choose Free.
6. Build command (exact):

   npm install && npm run build

7. Start command (exact):

   npm start

   `npm start` performs idempotent seeding/migrations and starts Express.
   Never run migrations/seed in the build command: the persistent disk is
   NOT attached during builds. First startup initializes the disk instead.

8. Under Environment, add exact variable names and values:

   NODE_ENV        production
   DATA_DIR        /var/data
   NODE_VERSION    22.16.0
   COOKIE_SECRET   <random secure secret, at least 32 characters>
   SEED_PASSWORD   <a separate random secure password>

   Generate TWO different random strings on your MAC Terminal:

   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

   Run twice; copy one for COOKIE_SECRET and one for SEED_PASSWORD. Do NOT
   share these publicly. SEED_PASSWORD is used only if the initial demo
   accounts are created. There is no actual private production password in
   the ZIP. The app checks COOKIE_SECRET length in production.

   Optional APP_ORIGIN = https://YOUR-SERVICE.onrender.com (set after URL is
   assigned). This restricts browser mutation requests to that origin.
   If you add a custom domain, set APP_ORIGIN to that custom domain.

9. CRITICAL: Add a persistent disk to the Web Service settings, BEFORE your
   first real deployment. Use:

   Disk name: shuka-persistent
   Mount path: /var/data
   Size: 1 GB or larger

   The site must keep /var/data/shuka.sqlite, /var/data/uploads/ and
   /var/data/backups/ on this persistent disk. Ensure DATA_DIR=/var/data.
   Render labels can shift; look for Disks or Persistent Disk in the service
   configuration. If service setup initially forces a deploy, attach the
   disk BEFORE creating real user accounts or uploads.

10. Click Create Web Service / Deploy. Render installs dependencies, builds
    the frontend, mounts /var/data, runs npm start, initializes SQLite and
    seeds demo data only when missing. Subsequent restarts preserve data.
11. Under Logs, confirm "Applied 001_schema.sql" on first run, then "Shuka
    listening". The normal log for subsequent boots says 0 new products.
12. Under Settings / Networking, obtain the URL:

    https://YOUR-SERVICE.onrender.com

    Render provides HTTPS/TLS on the onrender.com URL automatically.
13. Open that URL in a browser AND on a phone. Test category, cart and images.
14. Render's environment normally provides PORT automatically. Do not
    override it unless needed. Express listens on 0.0.0.0 using PORT.

Alternative: Render Blueprint deployment. The included render.yaml contains
all the same build, start, disk and environment settings. Choose New > Blueprint,
connect the repository, inspect the proposed paid Web Service and disk,
and approve. The blueprint automatically generates secure secret values.
The manual setup above helps you understand each required setting.

IMPORTANT: No production checkout requires paid APIs. Transactions are inside
SQLite. Persistent disks prevent loss on ordinary restarts, but do NOT mean
there is an automatic off-platform disaster recovery copy.

PART E — MAINTENANCE AND DAILY BACKUPS
--------------------------------------
Change your code on your Mac and redeploy:

   git add .
   git commit -m "Update Shuka"
   git push origin main

Render automatically redeploys commits if Auto Deploy is enabled. If disabled,
open Render dashboard > service > Manual Deploy > Deploy latest commit.
Do not delete or recreate the disk. A disk-backed service cannot scale to
multiple instances; Render may briefly interrupt service during redeploy.

View logs: Render dashboard > service > Logs.
Restart: Render dashboard > service > Manual Deploy > Restart service
(or the similarly named Restart command).
Edit secrets: Render dashboard > service > Environment; save and redeploy.

Automatic daily SQLite backup:
  In production backend/server.js schedules a consistent SQLite .backup
  operation every day at about 02:00 UTC. It writes files such as:

  /var/data/backups/shuka-2026-11-19.sqlite

  14 dated local copies are retained. Logs show Daily SQLite backup complete
  or Daily backup failed. You can also execute manually in Render Shell:

  npm run backup

  This uses better-sqlite3's online backup API, not `cp` on a live WAL file.
  A single backup file is a consistent snapshot of the DB.

Back up uploads TOO: /var/data/uploads. For full disaster recovery, regularly
copy both database backups AND all upload files OFF the Render disk to a
separate secure location. A backup saved on the same disk does not protect
against complete disk loss. A Render paid instance with Shell access can
run `tar -czf /var/data/backups/uploads-archive.tgz -C /var/data uploads`
but you must still transfer that archive off-platform. Use Render Shell or
an authorized secure transfer method supported by your Render account.

To restore after a problem:
1. Take the service offline briefly to prevent new orders and uploads.
2. In Render Shell, inspect /var/data/backups/ and select a known-good copy.
3. Safely stop the running SQLite writer before replacing database files.
   A reliable process is to switch the start command temporarily to a
   maintenance script or stop the service with the hosting controls.
4. Copy the chosen snapshot to /var/data/shuka.sqlite only while the server
   is stopped, and remove stale shuka.sqlite-wal / shuka.sqlite-shm only
   after the server has been fully stopped and you are restoring a complete
   consistent snapshot (never delete them while the database is open).
5. Restore the matching uploads directory from the same backup period.
6. Start the service and verify products, orders, and images.
7. Do not restore a historical DB without recognizing that later orders may
   be lost. Restore is a destructive recovery operation; preserve a copy of
   the current disk first.

PART F — TROUBLESHOOTING
------------------------
Npm fails:
  On Mac: `node -v` (need >=20), `npm cache verify`, then `npm install`.
  On Render: check Build Logs, confirm Runtime Node and root directory.
  If the lockfile is stale run npm install locally, commit the regenerated
  package-lock.json, then push. Native better-sqlite3 and sharp packages
  require a compatible Node platform. Use Node 22 on Render.

Missing COOKIE_SECRET:
  In Render service > Environment add COOKIE_SECRET with a 64-character
  hex string. In production this is mandatory. Redeploy after editing.

SQLite "unable to open database" or permissions:
  Confirm persistent disk mount /var/data, DATA_DIR=/var/data. SQLite needs
  WRITE permission in the directory, not only the database file.
  In Render Shell: `ls -la /var/data` and `df -h /var/data`.

SQLite "database is locked":
  The app uses WAL mode, a 10-second busy timeout and BEGIN IMMEDIATE.
  Check that only ONE service instance opens the database and the volume is
  NOT shared across independent writers. Check disk capacity and server logs.
  Do not use parallel extra services against the same database file.

Port in use locally:
  Run `lsof -nP -iTCP:3000 -sTCP:LISTEN`; stop the old app with Ctrl+C.
  Or use `PORT=3001 npm start` and visit http://localhost:3001.
  On Render leave PORT controlled by Render.

Images refuse to upload:
  Use JPEG/PNG/WebP/HEIC under 8MB each, up to 5 per listing. Real image
  bytes are inspected, not just the filename. Check write access to
  /var/data/uploads, disk free space, and Logs. Files must be submitted
  as multipart/form-data field `images`.

Blank web page:
  Check Build Logs for success from `npm run build`; verify frontend/dist
  exists after build. In browser DevTools Console/Network, check JS errors.
  Ensure Express `npm start`, not `vite`, is the Render start command.

UI loads but API calls fail:
  Open https://YOUR-SERVICE.onrender.com/api/categories in the browser.
  A JSON list means the API route works. Check Render Logs for server errors.
  Production client uses relative /api paths, not localhost.

Authentication cookies do not persist:
  Confirm HTTPS, correct system clock, same hostname, NODE_ENV=production,
  and COOKIE_SECRET set. Avoid mixing a custom domain with onrender.com
  during the same session. Cookie is Secure, httpOnly and SameSite Lax.
  If using a custom domain set APP_ORIGIN to https://your-domain.

Build fails:
  Make sure Node 22, `npm install && npm run build`, repository root.
  Reproduce on Mac: `npm install && npm run build`, fix output, push again.

Data disappears after redeployment:
  STOP using the service for real orders until corrected. Check DATA_DIR
  and disk mount match /var/data. If on Render Free, disk persistence is
  NOT supported: upgrade and attach a disk before live use. Do NOT assume
  temporary ./data is preserved between redeployments.
